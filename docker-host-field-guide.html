Field Guide: Standing Up a Docker Host to Take Workloads off TrueNAS

A repeatable playbook for deploying a clean Ubuntu cloud-init VM on Proxmox, hardening it, installing Docker + Portainer, and—most importantly—solving the storage / bind-mount migration so your existing Compose files keep working unchanged.

0. Overview & Goal

Right now your services run as Docker Compose stacks on the TrueNAS box itself. Every stack in this repo bind-mounts its data into /mnt/SSD/Containers/<app> using named volumes with driver_opts: o=bind (see paperless-ngx/compose.yaml, loki/, etc.). The plan:

  1. Spin up a dedicated Ubuntu Docker VM on Proxmox from your cloud-init template.
  2. Apply a consistent host baseline (the "first 5 things").
  3. Install Docker Engine and join it to your existing Portainer as an environment/agent.
  4. Make /mnt/SSD/Containers resolvable on the new host so the same Compose files deploy unchanged.
  5. Migrate stacks one at a time, keeping monitoring (Loki / Prometheus / Alloy) intact.
Design principle Keep the bind-mount path identical on the new host (/mnt/SSD/Containers/...). If the path matches, none of the Compose files in this repo need editing—only where that path physically lives changes.

1. Target Architecture

Compute

New Ubuntu VM on Proxmox (e.g. docker01), 2–4 vCPU, 4–8 GB RAM, QEMU guest agent on. Managed centrally from your existing Portainer.

Storage (the question)

Two viable models: (A) keep data on TrueNAS and mount it over NFS at /mnt/SSD/Containers, or (B) give the VM its own disk and migrate the data locally. Covered in §6–§9.

Networking

Reuse the shared Docker networks already in the repo: traefik (reverse proxy) and monitoring (Prometheus/Loki). Traefik can stay where it is or move too.

Observability

Grafana Alloy on the new host ships container logs to Loki via the Docker socket; Prometheus scrapes the new host. Just add the host as a new source—§10.

2. Build / Confirm the Ubuntu Cloud-Init Template

Based on your write-up at virtuallyboring.com — Ubuntu 26.04 Cloud-Init Template. If the template already exists, skip to §3.

# On the Proxmox node shell
export VMID=8001
export STORAGE=local-zfs        # your VM storage

# 1. Download the cloud image (26.04 'resolute')
wget -q https://cloud-images.ubuntu.com/resolute/current/resolute-server-cloudimg-amd64.img
qemu-img resize resolute-server-cloudimg-amd64.img 32G

# 2. Create the VM shell
qm create $VMID --name "ubuntu-2604-cloudinit-template" --ostype l26 \
  --memory 2048 --cores 2 --cpu host --sockets 1 \
  --net0 virtio,bridge=vmbr0 --agent 1 \
  --bios ovmf --machine q35 --efidisk0 ${STORAGE}:0,pre-enrolled-keys=0

# 3. Import disk + attach
qm importdisk $VMID resolute-server-cloudimg-amd64.img $STORAGE
qm set $VMID --scsihw virtio-scsi-pci --scsi0 ${STORAGE}:vm-${VMID}-disk-0
qm set $VMID --boot c --bootdisk scsi0

# 4. Cloud-init drive + serial console (needed by the cloud image)
qm set $VMID --ide2 ${STORAGE}:cloudinit
qm set $VMID --serial0 socket --vga serial0

# 5. Defaults baked into the template
qm set $VMID --ciuser youruser --sshkey ~/.ssh/id_ed25519.pub --ipconfig0 ip=dhcp

# 6. Convert to template
qm template $VMID
Tip Bake the qemu-guest-agent install into a cloud-init vendor snippet (or first-boot runcmd) so every clone reports its IP to Proxmox and supports clean shutdowns. Enabling --agent 1 alone does nothing until the agent is installed in-guest.

3. Clone & Size the New Docker VM

  1. Right-click the template → Clone → Full Clone (not linked—you want independence). Name it docker01.
  2. Set CPU/RAM for your workload (start 2 vCPU / 4 GB; bump per stack needs).
  3. Set a static IP or DHCP reservation—Portainer, Traefik, and Prometheus all need a stable address.
  4. If you choose the "local data" storage model (§7 Option B), add a second virtual disk now for /mnt/SSD so container data lives off the OS disk.
  5. Boot, then: sudo apt update && sudo apt -y full-upgrade && sudo reboot

4. First 5 Things to Change on Every Docker Host

Adapted from VirtualizationHowto — "The First 5 Things I Change on Every Docker Host", applied to this Proxmox/Ubuntu setup. Do these before you deploy a single stack.

4.1 — Cap container log growth

The default json-file driver never rotates; one chatty container can fill the disk. Set a global default in /etc/docker/daemon.json:

{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "5" }
}
Loki interaction You ship logs to Loki via Alloy, but the local json logs still accumulate on disk. Rotation here protects the host even though Loki is your long-term store. Keep max-file ≥ 3 so Alloy's Docker-socket tailer doesn't miss lines during bursts.

4.2 — Move Docker's data-root off the OS disk

Don't let /var/lib/docker (images, volumes, overlay layers) fill the root filesystem. Point it at a dedicated disk/dataset:

# add to /etc/docker/daemon.json
{ "data-root": "/mnt/docker-data" }

Stop Docker, move existing data, then restart:

sudo systemctl stop docker
sudo rsync -aP /var/lib/docker/ /mnt/docker-data/
sudo systemctl start docker
docker info | grep "Docker Root Dir"
Keep these separate data-root (images + Docker-managed volumes) is different from your application bind-mounts under /mnt/SSD/Containers. Both should live off the root disk, but they are two distinct concerns—don't conflate them.

4.3 — Harden access

  • Run as a dedicated non-root user in the docker group (your cloud-init ciuser is already this).
  • SSH keys only — in /etc/ssh/sshd_config.d/: PasswordAuthentication no and PermitRootLogin no.
  • Add no-new-privileges:true to stacks (this repo already does on most services—keep the convention).
  • Enable ufw: allow SSH + the ports you actually expose; deny the rest.

4.4 — Update OS + install core tooling

sudo apt update && sudo apt -y full-upgrade
sudo apt -y install htop curl vim git ncdu nfs-common unattended-upgrades
sudo dpkg-reconfigure --priority=low unattended-upgrades   # auto security patches

nfs-common is needed now if you go with the NFS storage model (§7 Option A).

4.5 — Set resource limits

Stop one runaway container from starving the host. Add to stacks that deserve guardrails:

services:
  app:
    deploy:
      resources:
        limits:   { cpus: "2.0", memory: 2g }
        reservations: { memory: 512m }

5.2 Add the host to your existing Portainer

Keep Portainer as your single pane of glass. Two ways to attach the new host:

MethodHowWhen to use
Portainer Agent (recommended) Deploy the agent container on docker01; add it in Portainer → Environments → Add → Docker Standalone → Agent. Secure, no Docker socket exposed over TCP. Best default.
Edge Agent Agent dials home to Portainer; no inbound port needed. If the host is on a different network segment / behind NAT. 
# Portainer Agent on the new host
docker volume create portainer_agent_data
docker run -d -p 9001:9001 --name portainer_agent --restart=always \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v /var/lib/docker/volumes:/var/lib/docker/volumes \
  -v /:/host \
  portainer/agent:latest
Git-backed stacks Point Portainer stacks at this repository (Git-based deployment) so the new host pulls the exact same Compose files you already version-control. Combined with identical bind-mount paths (§6), a stack moves hosts with zero edits.

6. The Storage Problem ★ (the heart of this migration)

Every stack here expects its data at /mnt/SSD/Containers/<app>/.... Example from paperless-ngx/compose.yaml:

volumes:
  paperless-media:
    driver: local
    driver_opts:
      type: none
      device: /mnt/SSD/Containers/paperless/media
      o: bind

That device: path must exist on whatever host runs the container. So the storage question is really: "How does /mnt/SSD/Containers appear on the new Ubuntu VM, and how does the existing data get there?" You have two clean models.

7. Mount Strategy: Two Models

Option A — Keep data on TrueNAS, mount over NFS

TrueNAS stays the storage authority. The Ubuntu host mounts the SSD dataset over NFS at the same path /mnt/SSD/Containers. Compose files don't change at all.

Pros: no data copy/cutover; TrueNAS snapshots & replication still protect the data; instant rollback (point the path back).

Cons: container I/O now crosses the network; NFS file-locking/permissions quirks for databases (Postgres/MariaDB/SQLite) can corrupt or slow them.

Option B — Migrate data local to the VM

Give the VM its own (virtual) SSD disk mounted at /mnt/SSD, rsync the data over once, and run everything locally.

Pros: best & most predictable performance; databases happy on local disk; host is self-contained.

Cons: a real cutover (stop → copy → start); you now own backups for this data (snapshot the Proxmox disk / back up to TrueNAS).

Databases over NFS — read this Do not run SQLite, Postgres, MariaDB, or Redis persistence on an NFS mount unless you've tested it hard. NFS locking semantics cause corruption and lock errors. Recommended hybrid: bulk/app data (paperless media, nextcloud files, Loki chunks) on NFS = fine; database volumes on the VM's local disk = safe. You can mix per-volume in the same Compose file.

Recommended pattern: hybrid

Data typeWhereWhy
App bulk data (media, documents, log chunks)NFS from TrueNASLarge, benefits from TrueNAS snapshots; latency-tolerant
Databases (pg/maria/redis/sqlite)Local VM diskNeeds POSIX locking + low latency
Docker images & data-rootLocal VM diskNever put overlay2 on NFS

8. The Persistent Mount in Ubuntu

This is the "persistent mount in Ubuntu" you asked about. The goal: /mnt/SSD/Containers is mounted automatically at every boot, before Docker starts its containers.

8.1 On TrueNAS — export the dataset over NFS

  1. TrueNAS UI → Shares → NFS → Add. Path = the SSD dataset backing /mnt/SSD/Containers.
  2. Set Allowed networks/hosts to the Docker VM's IP only.
  3. Map permissions so container UIDs line up (e.g. Loki uses 3001:3001; paperless/nextcloud have their own). Maproot only if you must—prefer matching UID/GID.
  4. Enable the NFS service.

8.2 On Ubuntu — persistent mount via /etc/fstab

sudo apt -y install nfs-common
sudo mkdir -p /mnt/SSD/Containers

# /etc/fstab  (TrueNAS_IP:/mnt/pool/dataset  →  /mnt/SSD/Containers)
TRUENAS_IP:/mnt/SSD/Containers  /mnt/SSD/Containers  nfs  \
  rw,_netdev,noatime,hard,nfsvers=4.1,x-systemd.automount,x-systemd.requires=network-online.target  0 0

sudo systemctl daemon-reload
sudo mount -a
df -h /mnt/SSD/Containers
OptionWhy it matters here
_netdevMarks it a network mount so the OS waits for the network.
x-systemd.automountLazy-mounts on first access and survives a NAS reboot without hanging boot.
x-systemd.requires=network-online.targetHelps ordering so the mount is ready before Docker.
hardRetries instead of returning I/O errors if the NAS blips (safer for data).
nfsvers=4.1Modern NFS; better locking & single-port firewalling than v3.

8.3 Make Docker wait for the mount

Even with the options above, force Docker to start only after the data is present so containers never start against an empty directory:

# /etc/systemd/system/docker.service.d/wait-for-mounts.conf
[Unit]
RequiresMountsFor=/mnt/SSD/Containers
After=mnt-SSD-Containers.mount
sudo systemctl daemon-reload
sudo systemctl restart docker
Why this matters If Docker starts before the NFS mount is ready, a bind-mounted volume will resolve to the empty local directory—your app boots "blank," may re-initialize, and could write into the local dir, masking the NFS share. RequiresMountsFor prevents that race.

8.4 Local-disk model (Option B) mount

If migrating data local instead, add the VM's second disk and mount it the same persistent way (no network options needed):

sudo mkfs.ext4 /dev/sdb
sudo mkdir -p /mnt/SSD
echo 'UUID=<uuid-of-sdb>  /mnt/SSD  ext4  defaults,noatime  0 2' | sudo tee -a /etc/fstab
sudo mount -a && sudo mkdir -p /mnt/SSD/Containers

9. Migrating the Compose Workloads

Move one stack at a time. The repeatable per-stack runbook:

  1. Freeze the stack on TrueNAS: docker compose down (clean stop = consistent data, especially DBs).
  2. Move the data (only for Option B / local model): 
    rsync -aHAX --info=progress2 \
  truenas:/mnt/SSD/Containers/<app>/ \
  /mnt/SSD/Containers/<app>/
    -aHAX preserves perms, ACLs, xattrs, hardlinks—critical so UID/GID and permissions survive.
  3. Verify ownership matches what the container expects, e.g. Loki: sudo chown -R 3001:3001 /mnt/SSD/Containers/loki.
  4. Deploy on the new host (Portainer Git stack or docker compose up -d). Same .env values; same paths.
  5. Validate: app loads existing data, logs clean, healthcheck green.
  6. Repoint Traefik/DNS to the new host, then decommission the old stack.
Order of migration Move stateless / low-risk stacks first (heimdall, homarr, uptime-kuma) to prove the pipeline, then data-heavy ones (paperless, nextcloud), and monitoring last so you keep eyes on the migration while it happens.
Watch the UID/GID TrueNAS apps sometimes run under apps-specific UIDs (e.g. 568/apps). On plain Ubuntu those UIDs differ. After rsync, confirm the numeric owner matches the container's expected user, or fix with chown / a user: directive. A "permission denied" on first boot is almost always this.

10. Monitoring: Loki, Prometheus & Alloy

Your observability stack (prometheus/, loki/, grafana/, alloy/) needs deliberate handling because it spans hosts during and after the move.

10.1 Decide where the stack lives

ApproachDetail
Leave Prometheus/Loki/Grafana on TrueNAS, add new host as a sourceLeast disruption. Just point Alloy on docker01 at the existing Loki, and add docker01 as a Prometheus scrape target. Recommended for the transition.
Move the whole stack to docker01Cleaner long-term if TrueNAS is being de-emphasized. Migrate Loki chunks (/mnt/SSD/Containers/loki) and Prometheus TSDB like any other stack—but mind retention/size and the monitoring network ownership.

10.2 The shared monitoring network

In this repo, the Prometheus stack owns/creates the monitoring network and Loki/Grafana/exporters attach to it as external. That works because they're on the same host. Across two hosts a Docker bridge network does not span machines. Options:

  • Keep each host's monitoring local: if Prometheus stays on TrueNAS, it scrapes docker01 over the LAN by IP:port (not via the monitoring bridge). On docker01, expose exporter ports to the host.
  • Or use an overlay / Tailscale if you want service-name resolution across hosts.
Pre-create the network on the new host If you deploy a stack that references monitoring as external before Prometheus exists locally, Compose fails fast. Pre-create it: docker network create monitoring (the Loki README already documents this).

10.3 Alloy on the new host

Alloy auto-discovers container logs via the Docker socket and pushes to Loki. On docker01 you simply:

  • Deploy Alloy with the Docker socket mounted (as in alloy/), pointing loki.write at your Loki endpoint (http://<loki-host>:3100 if Loki is remote).
  • Drop the TrueNAS-specific bits (the /var/log/journal TrueNAS mount, the :514 syslog receiver) unless this host should also receive syslog.
  • Add a Grafana label for the host so you can filter logs by source.

10.4 Add the new host to Prometheus

# prometheus scrape config — add a job for the new docker host
- job_name: docker01-node
  static_configs:
    - targets: ["10.0.5.x:9100"]   # node_exporter / cAdvisor on docker01

Run node_exporter (and optionally cAdvisor) on docker01 for host + per-container metrics, mirroring whatever TrueNAS exposed.

11. Tips & Tricks (Best Practices)

  • Keep paths identical across hosts. The single biggest lever—/mnt/SSD/Containers everywhere means Compose files are portable.
  • One .env per stack, never commit secrets. The repo's .gitignore already excludes .env; reproduce env values on the new host out-of-band.
  • Git-based Portainer stacks = drift-free deploys. The host pulls from this repo; you change code in one place.
  • Pin image tags / use WUD. You already run wud/ for update notifications—keep it pointed at the new host too.
  • Snapshot before cutover. Take a Proxmox snapshot of docker01 before each big migration so rollback is one click.
  • Test the NFS-reboot story. Reboot the VM and reboot TrueNAS independently; confirm x-systemd.automount recovers and Docker waits.
  • Mind file ownership early. Most first-boot failures after migration are UID/GID/permission mismatches—not app bugs.
  • Don't put overlay2 (data-root) or databases on NFS. Local disk only.
  • Stagger restarts. Use restart: unless-stopped (repo convention) and healthchecks so dependent stacks settle in order after a reboot.
  • Back up the new data path. If you go local (Option B), schedule a backup/replication back to TrueNAS so you don't lose the safety net you had.

12. Cutover Checklist

  • Ubuntu cloud-init template verified; docker01 cloned with static IP & guest agent
  • OS fully updated; core tools + nfs-common installed
  • Log rotation set in /etc/docker/daemon.json
  • data-root relocated off the OS disk
  • SSH hardened (keys only, no root); ufw enabled
  • Docker installed; host added to Portainer (agent)
  • Storage model chosen (NFS / local / hybrid)
  • /mnt/SSD/Containers persistently mounted (fstab + automount)
  • RequiresMountsFor drop-in makes Docker wait for the mount
  • First stateless stack migrated & validated end-to-end
  • UID/GID & permissions verified on migrated data
  • Data-heavy stacks (paperless, nextcloud) migrated
  • Alloy shipping docker01 logs to Loki
  • Prometheus scraping docker01 (node_exporter/cAdvisor)
  • Traefik/DNS repointed; old TrueNAS stacks decommissioned
  • Backups/snapshots configured for the new data path
